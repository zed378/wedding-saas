## P3-12: Public Page Caching and Invalidation

### Files to Create

1. **`backend/api/src/modules/publishing/cache-public-page.service.ts`** — application-layer cache for public invitations.
   
   Methods:
   - `get(invitationId: string, templateVersionId: string): Promise<PublicInvitationDto | undefined>` — cache key `public_page:{invitationId}:{templateVersionId}`, TTL 3600s (1 hour). Increment `wi_cache_hit_total` on hit, `wi_cache_miss_total` on miss (both label `namespace: 'public_page'`).
   - `warm(invitationId: string): Promise<void>` — fetch via `PublicInvitationService.bySlug`, store in cache with generation key.
   - `invalidate(invitationId: string): Promise<void>` — invalidate namespace `public_page:{invitationId}` (all template versions at once via generation counter, matching redis-cache.ts pattern).
   - Stampede protection: use Redis `SET NX EX` for a lock (`cache:lock:public_page:{invitationId}`, TTL 30s). On lock acquisition failure, poll for result with exponential backoff up to 5s. Only one request per invitation ID renders at a time.
   
   Inject: `CACHE` (CachePort), `PublicInvitationService`.

2. **`backend/api/src/modules/publishing/cache-template.service.ts`** — cache template definitions.
   
   Methods:
   - `getDefinition(templateVersionId: string): Promise<TemplateDefinition | undefined>` — cache key `tpl_def:{templateVersionId}`, TTL 3600s.
   - `invalidateAll(): Promise<void>` — invalidate namespace `tpl_def` via generation counter.
   
   Inject: `CACHE`, `TemplateRepository`.

3. **`backend/worker/src/pools/general/cache-invalidate.handler.ts`** — consume `cache.invalidate` job in the general worker pool.
   
   This is a general worker job (not domain-specific), so it lives in `backend/worker`, not `api-jobs`. It does NOT touch invitation status — it only invalidates cache keys in Redis, which requires no NestJS module context.
   
   Job payload type: `{ slug?: string; oldSlug?: string; invitationId: string; reason: 'unpublished' | 'slug_changed' | 'expired' | 'updated' | 'published' }`.
   
   Logic:
   - Use ioredis directly (same pattern as `cleanup-staging.handler.ts` — direct DB/Redis access, no NestJS DI).
   - Increment the generation counter for namespace `public_page:{invitationId}` using `INCR cache:gen:public_page:{invitationId}`.
   - If `reason === 'slug_changed'` and `oldSlug` is present, also increment generation counter for the old slug's lookup key.
   - Log `context: { event: 'cache.invalidated', invitationId, reason }`.
   
   Register in `backend/worker/src/handlers/index.ts` with pool `general`.

4. (Note: the `CachePublicPageService` lives in `api` and is what actually reads/writes the Redis cache during request handling. The worker handler only issues the `INCR` invalidation — these are separate responsibilities.)

## P3-13: Invitation Expiry Job and Renewal

### Files to Create

1. **`backend/api/src/jobs/invitation-expiry.handler.ts`** — daily expiry sweep, consumed by api-jobs process.
   
   Logic:
   - Query: `SELECT id, slug FROM invitations WHERE status = 'published' AND expiry_date < CURRENT_DATE AND deleted_at IS NULL FOR UPDATE SKIP LOCKED`.
   - For each: transition to `expired` via `InvitationStatusService.transitionWithin` with reason `'system: daily expiry sweep (BR-2.6)'`, actor `{ kind: 'SYSTEM' }`.
   - Enqueue `cache.invalidate` with `{ invitationId, slug, reason: 'expired' }` via `JobQueue`.
   - Enqueue `notification.send` with `{ template: 'invitation_expired', invitationId }` (wiring stub for P4-07).
   - Log `context: { event: 'invitation.expired', invitation_id, expired_at }`.
   - Idempotent: already-expired invitations are skipped by the WHERE clause.
   
   Inject: `InvitationRepository`, `InvitationStatusService`, `JOB_QUEUE`.
   
   Register in `backend/api/src/jobs/domain-jobs.ts` as `invitation_expiry_check` — following the exact pattern used for `order_expire_check` and `payment_reconciliation`.

2. **`backend/api/src/jobs/invitation-retention.handler.ts`** — retention chain: soft delete expired invitations 90 days old, hard delete soft-deleted invitations 30 days old, delete storage objects.
   
   Logic for soft delete:
   - Query: `SELECT id FROM invitations WHERE status = 'expired' AND expiry_date < CURRENT_DATE - INTERVAL '90 days' AND deleted_at IS NULL FOR UPDATE SKIP LOCKED`.
   - For each: set `deleted_at = now()`, enqueue `notification.send` with `{ template: 'invitation_soft_deleted_warning', invitationId, daysUntilHardDelete: 30 }` (three notifications at H-30, H-7, H-1 are `P4-07`'s concern; this job sends the H-30 notification on the day soft-deletion happens).
   
   Logic for hard delete (invitation data):
   - Query: `SELECT id FROM invitations WHERE deleted_at < CURRENT_DATE - INTERVAL '30 days' FOR UPDATE SKIP LOCKED`.
   - For each: enumerate all media for this invitation (`SELECT media_id FROM media WHERE invitation_id = :id`), delete storage objects via `StoragePort.delete('user-media', mediaKey(invitationId, mediaId, variant))` for each variant (`thumbnail`, `medium`, `large`), hard delete invitation row and all children (use Drizzle's cascade or explicit deletes in order of FK dependencies).
   
   Logic for removed-photo cleanup (OBLIGATION from P1-19):
   - Query: `SELECT invitation_id, id FROM media WHERE deleted_at IS NOT NULL AND deleted_at < CURRENT_DATE - INTERVAL '7 days' FOR UPDATE SKIP LOCKED`.
   - For each: delete storage objects via `@wi/storage`'s `mediaKey(invitation_id, media_id, variant)` for each of `thumbnail | medium | large`, hard delete media row.
   
   Register in `backend/api/src/jobs/domain-jobs.ts` as `invitation_soft_delete_cleanup`, following the same pattern as `order_expire_check`.
   
   Inject: `InvitationRepository`, `MediaRepository`, `STORAGE_PORT`, `JOB_QUEUE`.
   
   Note: The media hard-delete for individually removed photos runs inside `invitation_soft_delete_cleanup` as a second pass in the same job execution, not as a separate scheduled job. This keeps the storage cleanup consolidated in one daily scan, consistent with `docs/BACKEND/08` § Scheduled Job List.

3. **`backend/api/src/modules/order/renewal.service.ts`** — apply paid renewal orders to invitations (OBLIGATION from P3-05, ADR-077).
   
   Method: `applyRenewal(orderId: string): Promise<void>`.
   
   Logic:
   - Load order, guard `order_type === 'renewal'` and `status === 'paid'`.
   - Load invitation (owner-scoped via order).
   - Compute new `expiry_date = GREATEST(invitation.expiry_date, now()) + package_duration_months` (from `EntitlementsService`).
   - If `invitation.status === 'expired'`, transition to `published` via `InvitationStatusService`, reason `'system: renewal order paid'`.
   - Update `expiry_date` in one transaction with the status change.
   - Enqueue `cache.invalidate` if status changed to `published`.
   - Enqueue `notification.send` with `{ template: 'renewal_confirmed', invitationId }`.
   - Idempotent: check if renewal already applied by comparing `invitation.updated_at` or a dedicated `last_renewed_order_id` column (migration `0015`).
   
   Called by: event handler or job consumer for `order.paid` with `order_type = 'renewal'`. Add handler in `backend/api/src/jobs/domain-jobs.ts` that listens for the event emitted in `P3-05`'s payment webhook.
