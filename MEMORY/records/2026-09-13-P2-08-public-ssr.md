## What changed

`invitation.vizunicum.my.id/{slug}` now renders a real invitation, server-side: the whole
page and its sharing meta tags are in the HTML before any JavaScript runs. An address with
no published invitation gets a friendly page. The desktop view is letterboxed. A new
top-level route on this host is a failing test.

It also **found and fixed a defect in `P2-07`**: the payload was in the wrong shape and the
renderer could not read any of it (ADR-063).

## Why

Every task so far has produced something only the couple or the developer could see. This
is the guest's side, and `docs/FRONTEND/07` opens with the reason it cannot be a client-
rendered app: sharing bots scrape `og:*` without executing JavaScript, so an invitation
pasted into WhatsApp must produce its preview card from the bytes the server sent.

## How

**The payload had to be fixed first.** `P2-07` served `docs/API/08`'s example shape —
`events[].event_date`, `gallery`, `bank_accounts` — and the renderer resolves a section's
props from the *canonical* paths a template declares. Every path missed. The page came out
with the right sections and nothing in them. See ADR-063; the payload changed, `docs/API/08`
is amended, and a test now walks the fixture template's own declared paths against the
response.

**Slug resolution is one function** (`lib/slug.ts`), strategy-configurable, as
`docs/BACKEND/06` requires in those words. Both strategies are tested although only `path`
is configured: the document's reason for one implementation is that the two must not drift,
and an untested `subdomain` branch is exactly how it would.

**Normalize, then validate.** The other order rejects `ANDI-SARAH` outright — an address
typed from a printed card — and the editor stores slugs lowercase, so two rules for one
address would mean a link that works in one place and not the other.

**404 and 500 are different failures and must stay different.** `fetchPublicInvitation`
returns `null` for a 404 and **throws** for anything else. A page that renders "this
invitation does not exist" during an API outage tells a couple's guests something false and
permanent-sounding, on the one day it matters most.

**A client boundary that is still server-rendered.** `"use client"` does not mean "rendered
in the browser": Next renders the tree to HTML on the server and hydrates afterwards. The
boundary exists because the sections are interactive — a cover gate, a countdown, a copy
button, two form shells — and those modules now carry the directive themselves, since
needing the browser is a property of the module, not of whoever imported it.

**The renderer gained a `resolve` prop** rather than a mutable registry. A module-level
setter would make what a template renders depend on which application imported the package
first, and the editor and the public page could then disagree.

## Decisions made

- **ADR-063** — the public payload is in the canonical field-path shape.
- **A separate SSR suite**, run after the build and wired into `verify.sh`. The claim under
  test is about the bytes a production server sends; nothing in jsdom can check it.
- **A stub API for that suite**, not a seeded database. It makes the payload explicit and
  lets the 404 and the outage be produced on demand, which a database cannot. The real
  payload's correctness is `public-invitation.itest.ts`'s job.
- **No caching**, same reasoning as `P2-07`: the invalidation event arrives with `P3-09`.
  Asserted, so switching it on is deliberate.

## Security verification

- **Nothing unpublished renders** — that is `P2-07`'s query and `P2-07`'s tests; this app
  cannot reach the database at all. What is verified here is that it does not *undo* the
  decision: `"answers a malformed slug identically"` and `"renders the friendly page, not a
  framework error"` confirm a non-published address produces the same page whatever the
  reason, and `"the reason is never given"` asserts the page carries no "expired" or
  "deleted" wording.
- **The internal API address cannot reach a browser** — `server-only` in `lib/config.ts`
  and `lib/public-invitation.ts` makes a client import a build error. Not a test: a build
  failure is stronger than an assertion.
- **The slug is validated before use, from either source** — `slug.spec.ts`, 23 cases
  including `..%2F..%2Fetc`.
- **A new route cannot silently shadow an invitation** (R15) — `"has no top-level route
  that could shadow a slug"`, which reads the filesystem rather than trusting a convention.

**Mutation-adjacent check**: the SSR suite's "outage" case was written first against a
substring of the not-found wording and passed on the wrong page, because Next serializes
the layout's `notFound` slot into every document's flight payload. It now asserts the error
marker. The weaker version is recorded below rather than quietly replaced.

### The DoD item that is not met

`docs/FRONTEND/09` § Budget asks for *"section components loaded only for the active
template"*. The mechanism is in place — `TemplateRenderer` takes a `resolve` prop,
`Invitation.tsx` resolves all eleven names through `next/dynamic`, and the package exports
each section module as a subpath. **Turbopack merges them into one chunk anyway.**

Measured, not assumed: a document for a template with only a hero references an identical
chunk list to one with every section, and the chunk containing `GiftAccountList` and
`wi-hero` is fetched either way.

What it costs: 7.5KB gzip for the entire library, against a 150KB budget the page currently
uses 138.6KB of. A test pins the library at under 10KB, so the day it grows is a failing
test. `P2-13` owns the performance budget and is where this is picked up — that is also
when a second template family will make the split worth having.

## What did not work

**The payload was the wrong shape and every test passed.** `P2-07`'s 28 tests assert that
data is *present* in the response; none asserted it was *reachable under the name the
consumer asks for*. That distinction is the whole of the bug, and it survived a spec, a
review of `docs/API/08` and a mutation run. The new guard walks the template's own declared
paths — and was itself thin at first: the event section's fixture declared only
`events.*.title` and `events.*.venue_name`, so reverting `date` to `event_date` still
passed. A guard driven by a fixture is only as good as the fixture.

**A literal backspace in a test file. Again — the fourth time this session.** Writing
`/<script\b[^>]*>/` through a Python heredoc turned `\b` into 0x08 and
`check-text-sources.mjs` caught it, as it did the last three times. The rule recorded in
`P2-04` is now recorded here too: **code containing an escape or a regex is written with
the file tools, never assembled through a shell heredoc.** In the same session I also lost
a `node -e` invocation to backticks in a double-quoted shell string. Both failures have the
same shape and the same fix.

**A test that passed on the wrong page.** The outage case asserted that the body did not
contain the not-found wording. Next serializes the layout's `notFound` slot into every
document's flight payload, so the string is present in the bytes of a page that is not
showing it — the assertion would have failed on the correct page and passed on the wrong
one. Replaced with Next's error marker.

**Two runs lost to the rate limiter, in `P2-07`'s suite.** Recorded there; it recurred in
spirit here, in that a fixture problem looked exactly like a broken endpoint both times.

**A wart left in place**: during an API outage the error document's `<title>` still reads
"Undangan tidak ditemukan", because Next falls back to the not-found branch's metadata when
`generateMetadata` throws. The body and the status are right. Contorting the code to fix
the title of a page that only appears while the API is down was not worth it, and pretending
it was not there would have been worse.

## What to watch in production

- **A 500 on this host** is the API being unreachable, not a missing invitation. The
  distinction is deliberate and the alert should reflect it: a rising 500 rate is an
  outage, a rising 404 rate is slug enumeration.
- **The initial JS budget.** 138.6KB of 150KB with a three-section invitation. The next
  thing added to the client bundle is likely to break it, which is what the failing test is
  for.
- **A section rendering blank.** The boundary swallows it by design and nothing reports it
  yet.
