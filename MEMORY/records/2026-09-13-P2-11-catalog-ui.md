## What changed

A visitor can browse `/templates` without an account, filter by search, category and price,
open a template's detail page, see each of its sections rendered live, open the seeded demo
invitation, and press "Use This Template" — which survives a detour through login.

The catalogue and detail pages are server-rendered, carry their own metadata, and are the
only indexable pages in the application; a sitemap and `robots.txt` now exist.

Two gaps from earlier tasks were closed on the way: the create wizard's template list was
still hard-coded empty, and the staging deployment had never given the public invitation app
the address of the API.

## Why

The catalogue is where a stranger becomes a customer. `docs/UI-UX/11` is specific about the
one thing that must not go wrong: the demo has to set accurate expectations, so it must be
the product rather than a picture of it.

## How

**The URL is the catalogue's state.** Search, category, price and page live in the query
string and nowhere else. The filter form is a real `method="get"` form, so it works with
JavaScript off and is exactly what a crawler following a filter link gets; JavaScript only
adds the debounce. Typing uses `router.replace` so Back does not step through "E", "El",
"Ele"; a category change uses `push`. Changing any filter resets to page one.

**Every URL value is untrusted and degrades to the unfiltered catalogue.** A page of `0`,
`-3`, `1.5`, `dua` or `2abc` is page one — the last because `parseInt("2abc")` is `2`, and
the first version accepted it (a test caught it). An overlong category is dropped rather than
truncated into a different one.

**"View Live Demo" is a real invitation** (ADR-065). `docs/PLAN/07` § Demo Data had already
decided the demo is a seeded invitation owned by a system account. The template detail API
now returns `demo_slug`, **looked up** by ownership rather than derived from the seed's
`demo-{slug}` naming, which no document defines. The owner predicate is the one that
matters: without it, a customer's real wedding page would become every visitor's demo.

**Per-section previews are rendered, not screenshots.** The data model has no screenshots.
Each slide is the actual section drawn by the production renderer in `demo` mode from the
demo invitation's public payload — the exact bytes a guest receives — so a preview cannot
drift from the product. Slides are `inert`: a visitor cannot tab into a demo's copy button
from the catalogue.

**"Use This Template" is a link, and that is the whole logged-out flow.** It goes to
`/dashboard/new?template={id}`. `RequireAuth` carries the full URL, query string included,
through `/login?next=`, and `safeNext` hands it back (`P1-20`). Nothing is written to
storage, so a shared computer remembers nothing. A test drives the real functions through
the whole round trip.

**Indexable by exception.** The root layout is `noindex` for the entire app. The catalogue
and detail pages override it; filtered catalogue URLs render but canonicalise to
`/templates`, so filter combinations do not become hundreds of near-duplicate pages.
`metadataBase` was added to the root layout, because a relative canonical is ignored by the
crawlers that read it. The sitemap lists the home page, the catalogue and every published
template — never an invitation, which would be a directory of other people's weddings.

## Security verification

- **A customer's invitation is never offered as the demo** — *"never offers a customer's
  invitation on the same template as the demo"*. Mutation: removing
  `eq(invitations.ownerId, SYSTEM_ACCOUNT_ID)` fails exactly that test.
- **The internal API address stays out of the browser** — `server-only` on
  `lib/catalog-api.ts`; a client import is a build error.
- **No open redirect in the template flow** — the round-trip test drives the real
  `safeNext`, the allowlist `P1-20` built, with the exact href the detail page emits.
- **No invitation reaches the sitemap** — by construction: the sitemap reads only the
  catalogue API.

## What did not work

**The staging deployment could never have served an invitation.** `P2-08` built the public
page to read `API_INTERNAL_BASE_URL`, and the staging compose file never set it — so the
deployed container would have called `http://localhost:3000` from inside itself and returned
an error for every invitation. Nothing caught it because nothing has deployed Phase 2 yet.
Found while adding the same variable for the catalogue; fixed for both apps.

**The create wizard still offered no templates.** `P1-21` hard-coded `templates={[]}` with a
comment saying the catalogue API did not exist yet. `P2-01` built that API and the wizard was
never connected, so a signed-in user who opened "new invitation" directly was told there were
no templates on a product that has them.

**`parseInt` accepted `2abc`.** The first parser used `Number.parseInt`, so a mangled URL
landed on a real page nobody linked to. Digits-only now; the garbage-page test found it.

**Fake timers and `userEvent.type` deadlock.** user-event awaits its own timers between
keystrokes, which never advance under `vi.useFakeTimers()`. The debounce test uses
`fireEvent.change`; the behaviour under test is the debounce, not keystroke simulation.

**Docker restarted underneath the session** and the local Postgres came back on the default
port, which another project already held. The first test run failed with *role "wedding_app"
does not exist* against the wrong database. Restarted with `POSTGRES_PORT=55432`.

## What to watch in production

- **"View Live Demo" missing on a template that should have one** means the demo is not
  seeded, not published, or not owned by the system account — which is the intended failure
  mode, since a link to a not-found page is worse than no link.
- **A demo URL appearing in a search index.** The demo sets `seo_indexable: false`; if it
  shows up, the sitemap or a catalogue link has been indexed with it, and `P2-09`'s `noindex`
  is what should be keeping it out.
- **The catalogue returning 500** is an API outage by design — the page throws rather than
  showing "no templates", which would tell a visitor the product is empty.
