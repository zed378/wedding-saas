## What Changed

`deploy/helm/wedding-invitation/` is a chart that deploys the API and three worker pools to a Kubernetes cluster, with an ingress that routes the authenticated application and the public invitation surface to different hosts. It lints and renders; it has never been applied to a cluster.

## Why

The project owner asked for a `deploy/` directory holding Docker Compose and Helm charts. `P0-05` delivered the compose half.

The reason worth recording is the one behind the request. ADR-015 puts the MVP on a **single VPS**, and `docs/PLAN/18` records the accepted consequence as risk **R14**: one host, one failure domain. That is the right call for an MVP at Rp 139,000 a year. It stops being the right call at some point, and the expensive version of that moment is discovering the topology has never been written down while the site is down.

Writing the chart now costs a day and no operational risk. Writing it under pressure costs judgement, which is the thing you have least of during an outage.

## How

**Three worker pools, three Deployments, not one with three replicas.** `docs/BACKEND/08-JOBS-WORKERS.md` separates `media`, `general` and `cron` because they fail and scale differently. The media pool decodes untrusted images and needs hard resource caps; the cron pool must never run twice.

**The chart refuses to render two configurations.** This is the part I would defend hardest, because both configurations work fine on the day they are applied:

*A missing `image.tag`.* There is no default — not `latest`, not `.Chart.AppVersion`. `docs/DEVOPS/08-ROLLBACK.md` makes "roll back to the previous image" the entire recovery plan, and that sentence is meaningless against a moving tag: the image you want to return to may no longer exist under that name. Defaulting the tag would make the chart friendlier to install and useless to recover.

*`workers.pools.cron.replicaCount > 1`.* A second cron instance runs every scheduled job twice. The daily expiry sweep and the reminder emails are not concurrency-safe without leader election. The failure mode is what makes this a `fail` rather than a comment: nothing errors. A real couple gets two reminder emails, and the only trace is in their inbox. The cron pool also uses `strategy: Recreate` — a rolling update briefly runs two pods, which is the same hazard through a different door.

**The ingress splits two origins.** The application host carries `/api`. The invitation host carries **only** `/public`. Both proxy to the same Service; the separation is not about routing but about origin. Guest-submitted content renders on the invitation host, and if a guestbook entry ever survives sanitization, a script running there must not be same-origin with a logged-in dashboard. ADR-024 and `docs/SECURITY/02`.

**Secrets are not values, and there is no Secret template.** The chart reads credentials with `envFrom` from a Secret that already exists in the namespace. A chart that templates secrets from values puts every credential in the values file, which is the file that gets committed. `envFrom` also means adding a variable is a secret-store change rather than a chart change plus a redeploy (`P0-18`).

**Security context lives in one helper, applied to every workload.** Then verified in the *rendered output* rather than trusted from the helper — a helper that is defined but not included on one of four Deployments is exactly the kind of thing that reads correctly and ships wrong.

## Decisions Made

| Decision | Rationale | ADR |
|---|---|---|
| Chart written now, though the MVP does not use it | The escape from R14 is cheap to write calmly and expensive to write during an outage | — |
| `image.tag` required, no default | A moving tag makes `docs/DEVOPS/08` unexecutable | — |
| Cron pinned to one replica, enforced by `fail` | Double-running scheduled jobs fails silently and reaches real users | — |
| PostgreSQL and Redis are **not** subcharts | A datastore whose lifecycle is bound to the application release can be destroyed by `helm uninstall` | — |
| Secrets via `envFrom` on an existing Secret, no `Secret` template | Keeps credentials out of the values file, which is the file that gets committed | — |
| Frontends not in the chart | `web-app` and `public-invite` are static/SSR bundles on the CDN (ADR-013) | — |

## Definition of Done Verification

- [x] `helm lint --set image.tag=...` passes; a bare `helm lint` fails by design (see below)
- [x] `helm template` renders the full set with an explicit tag
- [x] Every workload non-root, read-only root, capabilities dropped, limits set — asserted in the render
- [x] No secret value in the chart
- [x] Both guard rails fire
- [x] Public invitation host routes only `/public`
- [ ] **Kubernetes schema validation — not performed.** Reason below.

## What Did Not Work

**Kubernetes schema validation is not possible on this machine, and I could not make it possible.** Two attempts:

1. `kubectl apply --dry-run=client` → `error loading config file "C:\Users\Zed\.kube\config": read ...: Incorrect function`
2. Retried with `KUBECONFIG` pointed at an empty file → `failed to download openapi: Get "http://localhost:8080/openapi/v2?timeout=32s": dial tcp [::1]:8080: connectex: No connection could be made`

The second error is the real one, and it is not a configuration problem: **`--dry-run=client` still contacts an API server** to download the OpenAPI schema it validates against. Without a cluster there is nothing to validate against, and no flag changes that. The honest position is that these manifests are known to be *well-formed* and to *render what they claim* — Helm parses every manifest it renders in order to sort them, so a successful render is real evidence of well-formedness — but they are **not** known to be accepted by any particular Kubernetes version. An `apiVersion` that has been removed, or a field renamed between versions, would not have been caught here.

Installing a local cluster (kind/minikube) is the right fix. It belongs to `P0-23`, which needs one anyway, rather than to a chart the MVP does not use.

**I claimed `helm lint` passed before it did.** Early in the task, before the `image.tag`
guard rail existed, `helm lint` passed on default values and I recorded that. Adding the
guard rail made a **bare** `helm lint` fail — correctly, since the chart now has a required
value — and I did not re-run the plain command until the closing pipeline. Two things worth
keeping from that:

The lesson is about *when* verification is run, not whether. A check performed before the
last change to the thing it checks is not a check; it is a memory. The closing pipeline is
what caught it, which is the argument for running one at all.

And the failure is ugly in a way worth knowing: `helm lint` renders in a tolerant mode that
downgrades the `fail` to `[INFO] Fail` and then reports the **downstream** breakage as the
error — `unable to parse YAML: ... line 52: mapping values are not allowed in this context`,
pointing at a line with nothing wrong with it. `helm template` prints the real message at the
real location. Anyone debugging that parse error from lint alone would lose an hour.

**No YAML parser was available** for a structural assertion over the render — neither `pyyaml` nor a `yaml` package in the workspace. The counted-grep assertions above are weaker than parsing would be: they prove each string appears four times, not that it appears under the right key on the right container. Worth upgrading when `P0-23` brings a cluster and a real validation step.

## Follow-Ups and Open Questions

- **`P0-23` must run `kubectl apply --dry-run=server` against a real cluster** before this chart is trusted. Carried on the task card and the board, not only here.
- **`NetworkPolicy` and `PodDisruptionBudget` are absent.** Neither is meaningful until workloads talk to each other in a real cluster.
- **Readiness still points at liveness.** `api.probes.readiness` defaults to `/health`, which deliberately touches no dependency — so a pod that cannot reach PostgreSQL is still sent traffic. `P0-13` ships `/readyz`; `NOTES.txt` prints a warning after every install until the two values differ.
- **`appVersion` is `0.0.0`** and stays there until there is something to version.

## What to Watch

**The chart will drift, quietly, because nothing runs it.** Compose is exercised every day; this is exercised never. `_helpers.tpl` will keep applying a security context to workloads whose environment variables have moved on, and the first sign will be a deploy that fails during the incident it was written for. `deploy/helm/verify.sh` exists for exactly this and takes about a second — but it only helps if something calls it, and with GitHub CI deferred nothing does. `P0-23` should wire it in.

**The cron guard rail is a `fail`, and someone under pressure will want to remove it.** If throughput ever demands more than one cron worker, the answer is leader election in the worker (`docs/BACKEND/08`), not a larger number in `values.yaml`. The error message says so, on purpose, because that is the moment the reasoning is needed.
