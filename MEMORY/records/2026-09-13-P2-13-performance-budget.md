## What changed

The public invitation was measured in a real browser for the first time, with the reference
template, representative photos and a throttled phone — and it was twice over budget: **LCP
5.2s** on Lighthouse's mobile Slow 4G profile. It is now **0.78–1.01s on Fast 4G** and
**2.9–3.3s on Slow 4G** (2.78–2.83s under Lighthouse's own simulated throttling), CLS 0.

On the way it found and fixed:

1. **The reference template's cover photo had never rendered on a public page.** The hero
   declared `gallery.photos.*.media_id`; the resolver narrows each photo to declared fields,
   and the public payload carries no `media_id`. The hero received photo rows with nothing in
   them. Every renderer test fed seed-shaped data with no URLs, so none could notice.
2. **The cover was lazy-loaded.** Every `Photo` was `loading="lazy"`, including the LCP image.
3. **The hero scrim failed WCAG AA over a light photo** — 45% → 65% black gives white text about
   3.4:1 over white, under a comment claiming 4.5:1 "against any photograph". Now 60% → 70%.
4. **Couple portraits were served as 1600w files** for a 140px square.
5. **Every guest of every wedding shared one rate-limit bucket.** The public page's server-side
   fetch to the API did not forward the guest's address, so `general-public`'s 100 a minute
   applied to the public page server as a whole. An invitation sent to a few hundred people
   would have started rendering its outage page. Found while adding the RUM forward.

And added: real-user monitoring (`POST /public/rum`), a browser performance suite in CI, pixel
contrast measurement, and 20 visual baselines (every section, both gallery variants).

## Why

`docs/FRONTEND/09`'s targets, and the card's point that a budget checked by hand drifts. The
card also inherited `P2-03`'s two browser-only DoD items (visual snapshots, contrast over a
photo) and `P2-08`'s per-template chunk measurement.

## How

**Measure first.** `e2e/fixtures/public-invite-stack.ts` serves the production `next start`
build against a stub API that returns the reference template read from the seed file and
photos from `e2e/fixtures/perf/` — generated by `generate-photos.mjs` at the worker's variant
widths (300/800/1600) and q80, weighing 17/85/145KB, roughly a real portrait photo. A
waterfall under throttling showed the cover preloaded at 0.7s and finishing at 5.2s.

**Then experiments, each served by the stub rather than intercepted** — `page.route` bypasses
DevTools throttling, and the first round of experiments was invalid for that reason:

| Change (Slow 4G, 4x CPU) | LCP |
|---|---|
| Baseline: 1600w cover from srcset, 1600w portraits, gallery fetched early | 5.2s |
| No other photos at all (upper bound of deferral) | 3.4s |
| Hero at 800w only | 4.0s |
| Both | 2.57s |
| Hero 800w + gallery `content-visibility` + portraits as thumbnails (shipped) | 2.9–3.3s |
| + blurred thumbnail placeholder (tried, removed) | ~80ms worse |

**Fixes**, in `@wi/template-renderer` (generic — no template-specific code):
- `Photo` gains `priority` (eager, `fetchpriority="high"`, `decoding="sync"`,
  `elementtiming="wi-lcp-image"`), `srcSet`, `sizes`; `variantSrcSet()` builds a srcset from
  whichever variants a row carries.
- `HeroClassic` uses `medium_url ?? url`, no srcset (ADR-067 §1). Gallery photos get srcset +
  sizes.
- `.wi-section:has(.wi-gallery-grid, .wi-gallery-carousel) { content-visibility: auto }`.
- Scrim 60% → 70%.

In the API: `medium_url` on gallery photos; `couple.<role>.photo` is the thumbnail;
`POST /public/rum` (strict zod, 204, `rum.web_vital` log line, `general-public` limit).
`metric`, `rating`, `page_kind` added to the sanitizer registry's `NOT_USER_TEXT` (enums, not
free text; deliberately not a bare `name`).

In `public-invite`: `WebVitals` (Next's `useReportWebVitals` → `sendBeacon`, keepalive fetch
fallback, never throws) on the invitation, preview and not-found pages; `app/public/rum/route.ts`
forwards ≤1KB bodies to the API; `lib/forwarded-for.ts` forwards `X-Forwarded-For` as received
(keeping the right-hand 512 characters of a padded header) from the rum forward and from both
server-side fetches. The invitation page's loader is wrapped in React `cache`.

**Lighthouse**, run ad hoc with system Chrome (`npx lighthouse@12`, not added as a dependency),
3 runs: LCP 2776/2783/2831ms, FCP ~0.8–0.96s, CLS 0.03 (before the `content-visibility` scope
fix below), TBT ~200–260ms, performance score 0.91–0.93. Its LCP breakdown attributes 83% to
"render delay": Lantern's pessimistic graph counts the framework scripts that start before the
paint.

## Decisions Made

ADR-067 (all eight points). In brief: hero at 800w with no srcset; portraits as thumbnails;
`content-visibility` on galleries only; scrim 60→70%; no LQIP placeholder; RUM as a same-origin
logged beacon with no URL; `X-Forwarded-For` forwarded unchanged; two throttling profiles, only
Fast 4G held to 2.5s pending `OQ-26`.

Also: the SSR suite's "section library under 10KB" test now subtracts the measured gzip size of
Next's compiled `web-vitals` library when Turbopack merges it into the section chunk (10.6KB
chunk = ~7.8KB sections + 2.8KB web-vitals), rather than raising the budget. The 150KB
whole-page budget is not adjusted.

**Mutation checks**: removing the `cache()` wrapper did **not** fail "asks the API once per page
view" — Next's request memoization already deduplicates identical GETs. The claim in the first
draft of the comment ("not deduplicated by Next") was wrong and was corrected; `cache` stays as
a guard because an `AbortSignal` on the fetch would silently opt out of that memoization. The
scrim and hero-declaration tests were run red against the old values (above).

**Stability**: the non-visual browser tests passed 3× repeated serially (21/21); the visual
tests 2× (4/4) after baselines were written.

## Security Verification

- **No new `:id` endpoint.** `POST /public/rum` has no identifier and reads no user data.
- **RUM carries no credential or couple identity**: `public-rum.itest.ts` › "refuses an unknown
  field rather than dropping it, so a URL can never ride along" and "logs the four fields and
  nothing else"; `web-vitals.spec.tsx` › "never sends the page's URL, which for a preview
  contains the token"; `public-performance.e2e.ts` › "beacons web vitals through the same origin
  to the API, carrying no address" (reads what the stub API received, since Playwright cannot
  read a beacon's Blob body).
- **Forwarding `X-Forwarded-For` does not let a client pick its bucket**: the API reads
  `req.ip` through `trust proxy` = `TRUSTED_PROXY_HOPS`, counting from the right; the forward
  passes the header unchanged so the proxy-written right-hand entries stay rightmost
  (`forwarded-for.spec.ts` › "forwards the header unchanged, never appending…", "keeps the
  right-hand end of a padded header…"). **Not verified on staging**: that the hop count there
  is right for a request arriving through the public page. See follow-ups.
- **Free text**: none accepted by the new endpoint; the three enum keys are registered as
  `NOT_USER_TEXT` and `check-sanitized-fields` passes.
- **Abuse of the forward**: bodies over 1KB are refused before any upstream call
  (`web-vitals.spec.tsx` › "refuses an oversized body without calling the API").

## Abuse Cases Covered

- A client posting a URL or token inside a report → 400, not logged.
- A client flooding reports → `general-public` limit on the API, per forwarded address.
- A client sending a huge body to the forward → 413 at the public page.
- A client forging `X-Forwarded-For` → only the left side is theirs; the API reads the right.
- A preview page's metrics → `page_kind: "preview"`, never the path.
- **Not covered**: a flood of valid reports from many addresses inflating log volume. One
  INFO line per report is cheap, but see What to Watch.

  Slow 4G / Lighthouse mobile** (2.9–3.3s in Playwright, 2.78–2.83s in Lighthouse, CLS 0).

- [x] **The bundle budget is enforced in CI.** — new `public-invite-budget` job in
  `.github/workflows/pr.yml` builds the page and runs `test:ssr` (150KB gzip initial JS; 10KB

- [x] **RUM is wired and reporting.** — end to end in a browser against the production build

## What Did Not Work

- **`page.route` for throttling experiments.** Intercepted responses bypass DevTools network
  emulation, so the first round of "hero at 800w" numbers (1.5s) were meaningless. Variants had
  to be served by the stub itself.
- **A blurred thumbnail placeholder** to get an earlier LCP. Chrome discounts an upscaled
  image's area, so the sharp image still became LCP, ~80ms later. Removed.
- **`content-visibility` on every section** — introduced a 0.03 CLS (Lighthouse and Playwright
  both saw it on the couple section). Scoped to galleries.
- **Believing the double fetch.** I assumed `generateMetadata` and the page each hit the API; a
  mutation showed Next already deduplicates. The comment was corrected.
- **`--update-snapshots=missing`** still reported the first write as a failure in this
  Playwright version; a plain `--update-snapshots` run wrote the baselines.
- **`--repeat-each` with parallel workers** failed instantly: each worker tried to start the
  stack on the same ports. Serial (`--workers 1`) is required for this file.
- **Lighthouse via Playwright's bundled Chromium** crashed on navigation (`Target closed`, then
  `EPERM` cleaning its temp profile). System Chrome worked.
- **`sendBeacon` bodies are invisible to Playwright** (`postData()` empty for a Blob), so the
  RUM browser test reads what the stub API received instead.

## What to Watch

- **`rum.web_vital` p75 LCP by `page_kind`** once staging reports. Lab says 0.8s on Fast 4G and
  ~3s on Slow 4G; Indonesian mobile networks at a crowded venue will say which is real.
- **Log volume**: up to five INFO lines per page view. A viral invitation multiplies it; sample
  before it matters.
- **429s on `GET /public/i/:slug` from the public page's address** — would mean the forwarded
  address is not reaching the limiter (hop count wrong on that path).
- **The Slow 4G tripwire (4s)** failing in CI means a change undid part of ADR-067.
