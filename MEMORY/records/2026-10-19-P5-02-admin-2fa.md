## What Changed

1. Implemented RFC 6238 Time-Based One-Time Password (TOTP) engine in `MfaService` (`backend/api/src/modules/auth/mfa/mfa.service.ts`) with HMAC-SHA1, 6-digit numeric codes, 30s period, and ±1 step (30s) drift tolerance.
2. Built application-layer AES-256-GCM encryption/decryption for TOTP secrets stored at rest in `user_mfa_factors.secret_encrypted` (`bytea`).
3. Implemented generation and validation of 8 single-use recovery codes in `XXXX-XXXX` format, stored hashed with SHA-256 in `user_recovery_codes`, and invalidated immediately upon first use.
4. Added mandatory 2FA interception in `LoginService.login()` for `admin` and `super_admin` roles: credentials verification issues a 5-minute signed JWT ticket (`mfa_ticket` or `setup_ticket`) without minting an access token until TOTP verification completes.
5. Added `StepUpGuard` and `/api/v1/auth/mfa/step-up` endpoint issuing 10-minute signed step-up re-authentication tokens for high-impact actions.
6. Created frontend 2FA pages and components in `@wi/admin`: `MfaEnrollPage`, `MfaVerifyPage`, and `StepUpModal`.

## Why

Administrative accounts have wide privileges over platform settings, moderation, and financial transactions. `docs/SECURITY/03` § Admin Session and `docs/PLAN/12` § Access Control mandate Two-Factor Authentication (TOTP) for all administrative logins and step-up re-authentication for high-impact operations.

## How

- `MfaService` implements Base32 encoding/decoding without external dependencies, TOTP calculation conforming to RFC 6238, and AES-256-GCM encryption with 12-byte IV and 16-byte authentication tags.
- `LoginService.login()` uses method overloads so existing service callers and integration tests testing regular user login (`role: 'user'`) continue to receive `Promise<Session>` without disruption, while HTTP login requests handle `LoginResult = Session | MfaChallengeOutcome`.
- `StepUpModal` wraps sensitive admin mutations, querying `/api/v1/auth/mfa/step-up` and passing `step_up_token` in the `X-MFA-Step-Up` header.

## Decisions Made

| Decision | Rationale | ADR |
|---|---|---|
| RFC 6238 TOTP with ±1 step drift tolerance | Accommodates mobile authenticator device clock skew up to 30s while maintaining tight security | ADR-097 |
| Application-layer AES-256-GCM for TOTP secrets | Protects against plaintext secret exposure in database dumps or SQL injections | ADR-097 |
| 8 single-use recovery codes hashed via SHA-256 | Ensures admin accounts cannot be permanently locked out if a device is lost | ADR-097 |
| 10-minute step-up re-auth validity | Prevents unattended administrative workstations from executing sensitive financial or account operations | ADR-097 |

## What Did Not Work

- Attempting to return `LoginResult` union directly without overloads in `LoginService.login()` broke TypeScript checking in 3 integration test files (`auth-session.itest.ts`, etc.) where callers expected `Promise<Session>` without discriminating. Introducing clean method overloads `login(email, password): Promise<Session>` and `login(email, password, { requireSession: false }): Promise<LoginResult>` preserved 100% backward compatibility while strictly enforcing the 2FA requirement.
