## Findings

### P5-10: audited, minimized live invitation support is implemented

The list performs count/projection reads inside a transaction, records one search event even for an empty result and records every selected invitation ID before returning. Detail awaits the audited repository bypass before histories or content completeness. The repository audits successful and nonexistent probes. Audit persistence failure rejects the operation; focused tests verify failure ordering and response denial.

Only GET list/detail methods exist on this surface. Detail returns operational owner/template/order/status information plus completeness counts and section keys; it does not return people, banks, media, internal family title or missing-field descriptions/values. Completeness derives its owner scope from the already audited invitation, not a client owner ID. Search strings use parameterized Drizzle conditions; pagination/search/reason bounds are present and audit reason passes the plain-text sanitizer.

Both controllers apply requireAuth, admin/super_admin role checks and the shared authenticated rate policy. SessionService re-reads the active user role and requires bounded MFA provenance for administrator accounts. The focused HTTP tests stub session resolution, so their pass does not independently certify cryptographic MFA provenance; that remains separate P5-14 session coverage. Enumeration is detectable via attributed search/read events, including empty searches. The named throttle test verifies a rejected policy decision returns 429 before service invocation; it does not independently benchmark Redis rate-limiter behavior.

### P5-11: SQL, revenue and cohort semantics match the documented contract

All metrics use one SQL statement/snapshot. Active invitation aggregates exclude soft-deleted invitations. Revenue reads currently paid order amounts and therefore excludes refunds once, rather than subtracting refunded amounts a second time. Daily/monthly/chart grouping follows order created_at in UTC, with zero-filled 30-day/six-month periods. Totals remain decimal integer strings; browser formatting uses BigInt.

Paid cohorts select DISTINCT invitation_id from paid/refunded history, deduplicating renewals. Publication cohort requires published_at on those same nondeleted invitations. Trial-only publication does not count as paid conversion. API and UI explicitly disclose that this is an operational lifetime cohort, not proof of payment-before-publication chronology. UI displays basis/refund/UTC/cache labels, visible cohort counts, charts with accessible data tables, loading/error/retry behavior and no fabricated fallback values.

The cache stores only aggregates for 30 seconds, and the mounted Redis adapter treats read/write failures as a miss/nonfatal cache failure. No customer identities or payment payloads are selected into dashboard output. Dashboard schema rejects undocumented query fields. Dashboard access is separately role/auth/rate guarded.

### Concrete unresolved edge limitation: soft-deleted support detail

`InvitationRepository.adminFindInvitationBypassingOwnership` deliberately returns soft-deleted rows for support (documented in its method comment). `AdminInvitationsService.getInvitationById` then unconditionally calls `PublishCheckService.check`, which calls `findOwned` and excludes deleted_at rows. Thus a valid administrative detail request for a soft-deleted invitation cannot complete and returns 404 from the completeness stage, even though its initial audited bypass found the row. The list already excludes deleted rows and P5-10's card/contract does not explicitly promise archived-detail support; classify this as a bounded support-scope limitation, not an unaudited disclosure or role bypass. The parent was notified before any edit; no repair or scope expansion was made in this review.

If archived support detail becomes required, define an explicit deleted/completeness-unavailable representation or a deliberately audited read path; do not weaken ordinary owner queries to expose deleted data. Current tests do not cover this edge, and no test is claimed to prove it; the finding follows directly from the three reviewed methods.
