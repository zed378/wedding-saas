## What changed

- **`POST /api/v1/invitations/:id/publish`** (`PublishController` → `PublishService`, publishing module):
  verified email → ownership + BR-4.2 (strict) → slug re-check → under the lock, paid or trial → transition +
  `published_at`/`expiry_date` in one transaction → `invitation_published` notification queued.
- **BR-2.8 trial**: new `draft → published` USER edge; eligibility (never `paid`, never `published`) from
  history; 3 days. Refusals: `TRIAL_ALREADY_USED`, `RENEWAL_REQUIRED`, `PAYMENT_PENDING`,
  `INVITATION_ALREADY_PUBLISHED`, `SLUG_*`, `INCOMPLETE_INVITATION`.
- **Trial notice** on the public page when `display.watermark` is true.
- **Fixed (critical)**: `publish-check` and `change-template` resolved canonical required fields against the
  editor API DTO — `events.*.date`, `gift.accounts.*`, `gallery.photos` always missing. New
  `toCompletenessDocument` for both.
- E2E fixture can start the public-invite app and verify an email.

## What Did Not Work

- **Nothing on the reference template could ever have been published** — the completeness defect above. It
  had been live since `P2-06` (2026-09-13); the editor's checklist would have shown the event date and gift
  accounts as missing to every couple, and `change-template` would have refused published invitations.
  Found only by the first end-to-end publish.
- A test inserted a `paid` invitation directly, without the history row a real payment writes, and the
  renewal rule (which reads history) treated it as never paid. The fixture now writes the row.
- `audit-status.itest.ts` used `draft → published` as its example of an impossible transition; BR-2.8 made
  it possible, so the example changed.
- Two long shell commands with nested quoting failed to parse; files were written with the editor tool.
