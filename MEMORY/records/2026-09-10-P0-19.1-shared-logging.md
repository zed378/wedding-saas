## What Changed

`packages/logging` (`@wi/logging`) now owns redaction, request context and job-trace propagation. The API and the worker each keep a four-line module that names their service and calls `createLogger`.

**The worker redacts for the first time.** That is the point of the task, not a side effect.

Two other things came out of it, both because the task had to touch files that were already wrong: a build guard that refuses a `pino()` call outside the package, and the removal of the hand-maintained workspace list from `backend/api/Dockerfile` — which `P0-19` had flagged and which was about to go stale a third time.

## Why

`docs/DEVOPS/06` § Mandatory Redaction: redaction happens "at the logger middleware level, **not relying on manual developer discipline each time**".

`P0-15` shipped the worker's logger with this comment on it:

> NOTE: this does NOT redact. … Until it can, the worker logs only fields it constructs itself — job names, ids, durations, error messages — and never a whole payload. That is a real limitation and it is written down rather than assumed.

That is exactly the arrangement the document forbids, described accurately. The `P0-15` record named `P0-19` as the place to fix it. `P0-19` did not, and paid for it in the same task: the `pino-pretty` crash-on-startup fix had to be written **twice**, once per copy, and the `P0-19` record says so.

Two tasks of deferral is enough. A comment is not a mechanism.

## How

**The package exports a factory, not a logger.** `createLogger({ service }, destination?)`. A ready-made singleton would need the package to read `SERVICE_NAME` on behalf of its consumer, and the worker sets a different one per pool (`worker-general`, `worker-media`, `worker-cron`).

**The API pre-binds `logSecurityEvent` rather than re-exporting it.** The package's version takes the logger as its first argument, which is right for a package and wrong for a call site: passing `logger` instead of `securityLogger` would compile, run, and silently move a security event out of the 1-year retention stream into the 90-day one. Binding it in `backend/api/src/shared/logging/logger.ts` means that mistake cannot be made in that process. There are no call sites yet — the binding exists so the first one cannot get it wrong.

**A build guard replaces the comment.** `scripts/check-logger-construction.mjs` refuses a `pino()` call anywhere outside `packages/logging/src/`, blocking in `scripts/verify.sh` and `.githooks/pre-push`. Tests are exempt: a test that builds its own instance to capture output is doing the opposite of hiding a leak, and `logging.spec.ts` does exactly that on purpose.

**`createLogger` gained an optional destination so it could be tested at all.** See *What Did Not Work* — the inherited suite could not have caught redaction being deleted.

**The Dockerfile's manifest list is gone** (ADR-036). `pnpm fetch` populates the store from the lockfile alone, so the dependency layer caches on `pnpm-lock.yaml` and there is no inventory of workspace members to keep current. `pnpm --filter @wi/api... build` (trailing dots) takes the build order from the dependency graph for the same reason.

## Decisions Made

| Decision | Rationale | ADR |
|---|---|---|
| One logging package; each surface owns its instance | The duplicated crash fix in `P0-19` is the cost of not doing it | ADR-035 |
| A build guard, not a comment | The comment survived four tasks and changed nothing | ADR-035 |
| `logSecurityEvent` pre-bound in the API | The wrong logger compiles and quietly changes retention | ADR-035 |
| `createLogger` takes an optional destination | Otherwise no test can assert what the factory produces | ADR-035 |
| Dependency layer keyed on the lockfile | A hand-maintained list of members fails silently, and had already failed once | ADR-036 |

## Abuse Cases Covered

- A developer logs a whole request object containing `password` and `authorization` — covered, both from the API and now from the worker.
- A future surface (`admin`, a second worker) builds its own pino instance because that is what pino's own documentation shows — blocked by the guard before push.
- A security event is sent to the application logger, quietly losing 9 months of retention — impossible in the API, which binds the stream.

## What Did Not Work

**1. The inherited test suite could not have caught redaction being deleted.**

`logging.spec.ts` (from `P0-12`) builds its own pino instance with a *copy* of the formatters and asserts those redact, with a comment explaining that importing the real logger would write to stdout through a transport worker that a test cannot capture. The comment is true and the conclusion was wrong: it means the suite tests the formatters, not `createLogger`. Delete the `log` formatter from `logger.ts` and all 39 assertions still pass, because none of them call it.

This is the same failure as `P0-12`'s own redaction test, which generated its payload from `REDACTED_KEY_NAMES` so removing a key removed it from both sides. **A test written from the shape of the code it tests verifies consistency, never correctness.** Twice now, in the same file.

Fixed by giving `createLogger` an optional destination and writing `logger.spec.ts` against the real factory. Measured, not assumed: the mutation numbers are in the table above.

**2. `import.meta` is a compile error in a CommonJS output file.**

The worker's copy used `createRequire(import.meta.url).resolve("pino-pretty")` because the worker is ESM. The package emits CommonJS, so that does not compile. Plain `require.resolve` is correct here, and if the package is ever consumed from an ESM build the `ReferenceError` lands in the same `catch` and the result is structured JSON — safe either way.

**3. The worker image never built its workspace dependencies, and nothing had noticed.**

`backend/worker/Dockerfile` ran `pnpm --filter @wi/worker build` — no trailing dots — so `@wi/schema`, `@wi/storage` and now `@wi/logging` had no `dist/`. It had been latent since `P0-15` because the worker had no *type-level* import of a workspace package. `@wi/logging` was the first, and the image build failed outright:

```
src/logger.ts(2,30): error TS2307: Cannot find module '@wi/logging'
```

A build that fails loudly is the good version of this bug. The API image had the same shape of latent problem in its own build step.

**4. `pnpm fetch` refused, then `--offline` refused, for two different reasons.**

`pnpm fetch` exits 1 with `ERR_PNPM_IGNORED_BUILDS` unless `pnpm-workspace.yaml` is present, because that file carries the `allowBuilds` decisions — correct behaviour, and worth knowing. Then `pnpm install --offline` failed with `ERR_PNPM_NO_OFFLINE_META`: pnpm 11 verifies the lockfile against supply-chain policies on every install and that check reads registry metadata `pnpm fetch` does not mirror. Settled on `--prefer-offline` and wrote down that the stronger claim is not available.

**5. A local-stack failure mode that looks like healthy.**

Host port 5432 was already taken by something else. Compose failed to program the container's networking, and the postgres container ended up **running, reporting `healthy`, and attached to no network at all** — `pg_isready` passes inside its own namespace. The API's DNS lookup for `postgres` then escaped to the host resolver and got a public address, so `/readyz` reported a 2-second database timeout while `docker compose ps` showed four healthy containers. `POSTGRES_PORT=55432 REDIS_PORT=56379` and a clean `down`/`up` fixed it. Nothing in this repository caused it, but the next person to see "healthy" beside a container that cannot be reached should read this paragraph.

## Follow-Ups and Open Questions

- **`request-id.middleware.ts` imports `logger` from the API's local module and `runWithRequestContext` from the package.** Correct, but it reads as inconsistent. Left as-is: the singleton genuinely is the API's, the context genuinely is the package's.
- **The guard belongs in ESLint once `P0-17` wires it.** A `no-restricted-imports` rule with a path exception is the same check with better ergonomics and editor feedback. The script works today, with CI deferred.
- **`packages/logging` has no `pino-pretty` devDependency**, so `prettyTransport()` always returns `{}` inside its own test run. That is what these tests want, but it means the pretty path is exercised by no test anywhere — only by running the API locally. Low value to fix; recorded so nobody assumes it is covered.
- **Redaction is by key name only.** A credential embedded in a free-text message — `"connection to postgres://user:hunter2@host/db failed"` — passes through untouched, and `backend/api/test/http-contract.spec.ts` demonstrates it reaching the log while being kept out of the HTTP response. Server-side logs may legitimately contain it; a value-shaped scan over every log line is a different and much more expensive control. Unchanged by this task, restated because an extraction is a natural moment to assume it was handled.

## What to Watch

**The test exemption in the logger guard is the hole.** Any file named `*.spec.ts` may build a pino instance. That is deliberate and it is also exactly where someone will put a helper that later gets imported by non-test code.

**Two of the three hand-maintained lists `P0-19` warned about are still there** — `check-tenant-scope`'s allowlist and the redactor's key set. The Dockerfile's is gone. The redactor's is the dangerous one, because it fails by omission: a new sensitive field name added to a table is not added to `REDACTED_KEY_NAMES` by anything, and the symptom is a value in a log nobody reads until they need to.

**`pnpm fetch` means the dependency layer rebuilds on any lockfile change.** If image build time becomes a problem, that is the first thing to look at — and the answer is not to bring the manifest list back.
