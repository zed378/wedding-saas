## What Changed

`GET`/`POST /invitations/:id/gallery`, `PATCH`/`DELETE /gallery/:photo_id`, and
`POST /gallery/reorder`. A gallery entry places a **ready** photo on an invitation with an
order, a caption and at most one cover.

Also, on the same branch and as its own commit: the timing tests in `password.spec.ts` got a
budget that matches what they cost. They had failed two gates as timeouts.

## Why

`docs/API/04` § Gallery, `docs/DATABASE/06`, BR-8.1, and `docs/PLAN/11` § Deletion.

## How

**A gallery entry is a placement, not a photo.** The photo is the `media` row — `P1-17`
created it, `P1-18` made it `ready`. The entry says where on this invitation it appears.
Keeping them apart is what makes `docs/PLAN/11` § Deletion coherent: removing a photo deletes
a placement and *soft*-deletes a file, and those are different operations on different rows.

**Only `ready` media may be attached.** A `processing` row has not been scanned, decoded or
EXIF-stripped; a `failed` one has no file. Attaching either puts an unscanned or absent image
on a page hundreds of guests open — the outcome `P1-18` exists to prevent, arriving through a
different door.

**"Not this invitation's media" is a 404, not a 422.** The media id arrives in a request body,
so `docs/SECURITY/05` § 6 applies: "belongs to someone else" and "does not exist" must be
indistinguishable. A helpful 422 saying "that photo is not ready yet" would confirm the id
exists, reintroducing the enumeration oracle ADR-018 removed everywhere else.

**The check is `media.invitation_id = :this_invitation`, not "does this user own it".** The
distinction `P1-11` found on `photo_media_id`: a photo from the user's *other* wedding is
still the wrong photo, and the looser check would let it through. A test names exactly that
case.

**Exactly one cover, cleared by every path that sets one.** Attach and update both call
`clearCover` first. If only one of them did, "exactly one" would hold on one path and not the
other — and the failure is invisible until the editor and the public page disagree about
which photo is the cover.

**Reorder is wholesale or nothing.** The supplied list must be exactly this invitation's
photos, each once — checked inside the transaction that writes. A partial application leaves
the user looking at an arrangement nobody chose. The "no foreign id" half is also a tenancy
control: without it, another invitation's photo could have its `display_order` rewritten by a
request shaped like a preference.

**The quota is held under a `FOR UPDATE` lock**, the same shape `P1-17` arrived at, and proved
the same way — a probe holding `FOR NO KEY UPDATE`, which conflicts with `FOR UPDATE` and not
with the foreign key's own `FOR KEY SHARE`.

## Decisions Made

| Decision | Rationale |
|---|---|
| Only `ready` media may be attached | A `processing` row is unscanned; a `failed` one has no file |
| Not-this-invitation's media is a 404 | `docs/SECURITY/05` § 6. A 422 would confirm the id exists |
| The same photo cannot be attached twice | A second entry means nothing to a viewer and would let 200 uploads become 400 gallery slots |
| The cap counts **gallery entries**, at the same 200 as the media cap | The upload path already bounds media rows; without an entry cap, one photo attached repeatedly would evade it. Duplicate-refusal makes them equivalent in practice, and both bounds are stated rather than one implied |
| `display_order` is not accepted on attach | A new photo is appended; rearranging is what `/reorder` is for. A client that could set it on attach could interleave into an order the couple chose |
| Reorder is a `POST` returning **200** | Nothing is created, so not 201; the body replaces the whole order rather than amending it, so not `PATCH` |
| Delete removes the placement and **soft**-deletes the media | `docs/PLAN/11` § Deletion, verbatim. The status stays `ready`: the photo was fine, it is retired rather than rejected |
| A gallery may have no cover at all | A template with no cover section should not oblige the user to nominate a photo that is never shown |

| Control | Requirement | How it was verified |
|---|---|---|
| Attaching another invitation's media is 404 | Card DoD 1, `SECURITY/05` § 6 | Three tests — another tenant, another invitation of the same user, a template asset. **Mutation**: dropping `eq(media.invitationId, invitationId)` fails all three |
| Exactly one cover | Card DoD 2 | Four tests. **Mutation**: removing `clearCover` from the update path fails `"promoting an existing photo clears the previous cover too"` — the attach path's test still passes, which is why both exist |
| Reorder is wholesale | Card DoD 3 | Five tests, each asserting the rows are **unchanged**. **Mutation**: removing the set comparison fails all five |
| The quota holds under concurrency | Card DoD 4, BR-8.1 | `"the attach takes a conflicting row lock on the invitation"` plus six concurrent attaches. **Mutation**: removing `FOR UPDATE` fails **both** |

| Cross-tenant writes through the gallery | `SECURITY/05` § 1, § 7 | Five repository methods exercised directly, because the service's own check masks them |

## Abuse Cases Covered

Attaching another tenant's photo; attaching a photo from the same user's other invitation;
attaching a template asset; attaching an unscanned or failed upload; attaching one photo
repeatedly to inflate the gallery; rewriting another invitation's `display_order` through a
reorder list; smuggling `display_order` or `invitation_id` through an attach body.

## DoD Verification

- [x] Attaching another invitation's media returns 404. Three variants of "another".
- [x] Exactly one cover photo can exist; a test asserts the previous one is cleared. Two
      tests, one per path that can set a cover.
- [x] Reorder with a foreign or missing id is rejected wholesale, not applied partially.
      Every case asserts the rows are byte-identical afterwards.
- [x] Quota holds under concurrent requests. And the lock that makes it hold is proved
      directly rather than inferred from a race that might not happen.

## What Did Not Work

**1. `password.spec.ts` failed two gates as a timeout before being diagnosed.** It was noted
as "probably flaky" at the start of the session and left alone; it then cost two full
`verify.sh` runs on unrelated branches. The cause was mundane: fifteen argon2 operations at
64 MiB against vitest's 5s default, under the full suite in parallel. Fixed with an explicit
60s budget, which weakens nothing — the assertion is a **ratio** between two paths measured in
the same interleaved loop, so a busier machine moves both numbers.

The lesson is about the diagnosis, not the fix: "probably flaky" was a guess, and acting on it
a week later would have been the same work at a worse moment.

**2. The reorder POST returned 201.** Nest's default for `@Post`. Nothing is created by a
reorder, and the test caught it immediately — but it is worth noting that the default is a
trap on every POST that is not a creation.

**3. The concurrency test caught the missing lock here, and did not in `P1-17`.** Same shape,
different outcome: the attach path does a read, a second read and an insert inside its
transaction, so six concurrent callers reliably interleave, where `P1-17`'s shorter path did
not. The deterministic lock probe is kept in both regardless — the difference between them is
timing on one machine, which is not something to rely on.

## Follow-Ups and Open Questions

- **The grace-period hard delete does not exist.** `docs/PLAN/11` § Deletion wants the
  physical file removed by an async job after about seven days. Soft-deleted media currently
  accumulate in `user-media` forever. That job belongs with the Phase 4 sweeps, beside
  `invitation_soft_delete_cleanup`; raised there rather than left implied.
- **`GET /invitations/:id/media` and `DELETE /media/:media_id`** are still unbuilt — the other
  two endpoints in `docs/API/05`. Neither `P1-17` nor this card owns them. The gallery delete
  covers the user-facing case; a media list would be an editor convenience.
- **A cover is not required at publish time.** If a template's cover section turns out to need
  one, that is a `P2-06` publish-check rule, not a gallery rule.

## What to Watch

**`clearCover` is called from two places and must stay called from both.** "Exactly one
cover" is not a database constraint — it cannot be, without a partial unique index this
schema does not have — so it is an application invariant held by two call sites. A third
path that sets `is_cover` and forgets would produce two covers, and the symptom is two
screens disagreeing rather than an error.

**The quota is now bounded in two places**: media rows at upload (`P1-17`) and gallery
entries at attach (here). They are the same number and they count different things. If one is
ever changed, the other needs the same change, or a user hits a limit whose message names the
wrong resource.
